HWGUI GTK4 — User Guide

Port of HWGUI from GTK2 to GTK4.
This document describes the principles, directives and usage of the GTK4 resources in HWGUI.

1. Overview

HWGUI is a GUI library for Harbour that provides a single API for both Win32 and Linux (GTK) applications. The GTK4 version is a parallel port of GTK2, keeping API compatibility at the Harbour level — that is, the same application code builds against both backends.

1.1. Why GTK4?

  • GTK2 is end-of-life — no modern support, no integration with Wayland, HiDPI or contemporary themes.
  • GTK4 offers better integration with KDE, GNOME and Wayland via xdg-desktop-portal.
  • Native HiDPI, scaling and GPU acceleration support.
  • Works transparently with Harbour Unicode.

1.2. Port principles

  1. Parallelism, not replacement. GTK2 and GTK4 coexist in the same repository. The application chooses which one to link.
  2. No #ifdef pollution. Code specific to each toolkit lives in separate files, not in conditional branches inside the same file.
  3. Harbour API unchanged. User code does not need to know whether it runs on GTK2 or GTK4.
  4. Each toolkit has its own directory and its own .hbp. source/gtk4/ for the new backend; source/common/ only for what compiles in every toolkit.

2. File structure

PathDescription
source/gtk4/ Implementation of GTK4 widgets, windows, dialogs and controllers.
include/hwgtk4.h Header with definitions specific to the GTK4 backend.
hwguiGTK4.hbp / .hbc / .hbm Project and build files for the GTK4 backend. Produce lib/hwgui.a.
procmiscGTK4.hbp Utility library (editor, processing) for GTK4. Produces lib/procmisc.a.
utils/bincnt/bincntGTK4.hbp Binary container manager built against GTK4.
source/common/editor/hcedit_l_gtk4.c Text editor (Linux) ported to GTK4.
Rule of thumb: if a file uses APIs exclusive to GTK4 (GtkFileDialog, gtk_widget_get_width(), g_list_model_*, etc.), it must live in source/gtk4/ or carry a _gtk4 suffix.

3. Building

3.1. Requirements

  • GTK 4.10+ (ideally 4.20+ for GtkFileDialog)
  • Harbour 3.2+ with hb_thread support
  • pkg-config and gtk4.pc installed
# Check GTK4
pkg-config --modversion gtk4

# Check Harbour
harbour --version

3.2. Building the HWGUI library

The library is generated as lib/hwgui.a, for both GTK2 and GTK4 — what distinguishes the two backends is the .hbp used during the build, not the name of the generated file. 

cd hwgui

# GTK2 backend
hbmk2 hwgui.hbp
# Produces: lib/hwgui.a (built with GTK2)

# GTK4 backend
hbmk2 hwguiGTK4.hbp
# Produces: lib/hwgui.a (built with GTK4) — overwrites the previous one
Warning: both versions produce lib/hwgui.a at the same path. It is not possible to keep GTK2 and GTK4 installed at the same time in the same directory. To switch backends, rebuild the library from the corresponding .hbp.

3.3. Building the utility libraries

The same applies to the utility libraries: the backend-specific .hbp produces lib/procmisc.a in both cases. 

# GTK2 backend
hbmk2 procmisc.hbp
# Produces: lib/procmisc.a (GTK2)

# GTK4 backend
hbmk2 procmiscGTK4.hbp
# Produces: lib/procmisc.a (GTK4) — overwrites the previous one

3.4. Building a user application

The application references the .hbc file matching the backend it wants to use. Because the libraries share the same name (hwgui.a, procmisc.a), the .hbc is what points to the correct path — and the application links against the same library name in both cases.

Backend .hbc to include Libraries linked
GTK2 hwgui.hbc + procmisc.hbc lib/hwgui.a, lib/procmisc.a
GTK4 hwguiGTK4.hbc + procmiscGTK4.hbc lib/hwgui.a, lib/procmisc.a
Practical implication: since the libraries share the same name, the .hbc is what determines which backend is used at link time. Make sure you rebuild lib/hwgui.a and lib/procmisc.a with the desired backend before building the application.

Example myappGTK4.hbp:

# myappGTK4.hbp

{linux}hwguiGTK4.hbc
{linux}procmiscGTK4.hbc

-L.

-n -w1

-omyapp

myapp.prg

The .hbc adds -lhwgui -lprocmisc to the link line, but points to the path where the GTK4 libraries reside. That is, the .a name is the same, but the content is GTK4.

4. Using GTK4 in Harbour code

The high-level API (classes HWindow, HDialog, HButton, HGet, HBrowse, etc.) is identical between GTK2 and GTK4. The code below works on both backends: 

#include "hwgui.ch"

FUNCTION Main()
   LOCAL oWnd, oBtn

   INIT WINDOW oWnd TITLE "GTK4 example" SIZE 400, 200

   @ 20, 20 BUTTON oBtn CAPTION "Click" SIZE 120, 30 ;
      ON CLICK { || hwg_MsgInfo( "Hello GTK4!" ) }

   ACTIVATE WINDOW oWnd
RETURN Nil
Tip: to test the same application on both backends, simply keep two .hbp files — one linking hwgui.hbc, the other linking hwguiGTK4.hbc.

5. Themes, appearance and CSS

GTK4 has a cascading style system (CSS) with multiple priority layers. Understanding this hierarchy is essential to predict which colour wins when two rules apply to the same widget.

5.0. CSS hierarchy in GTK4

Each CSS provider is registered with a priority. The higher the number, the later it is applied and, therefore, the more it wins in case of conflict.

Constant Value Used by in HWGUI GTK4
GTK_STYLE_PROVIDER_PRIORITY_FALLBACK 1 Reserved for GTK (internal fallback).
GTK_STYLE_PROVIDER_PRIORITY_THEME 200 System theme (Adwaita light/dark, Breeze, etc.).
GTK_STYLE_PROVIDER_PRIORITY_SETTINGS 400 User settings (e.g. gtk-theme-name).
GTK_STYLE_PROVIDER_PRIORITY_APPLICATION 600 set_css_data() in control.c — used by HWG_SETFGCOLOR, HWG_SETBGCOLOR and HWG_CSSLOAD.
GTK_STYLE_PROVIDER_PRIORITY_USER 800 hwg_install_entry_css() in window.c — entry geometry reset (and, in the current code, also hard-coded light colours).
USER + 1 801 HWG_CSSLOADFILE in control.c — the application's theme.css.

Effective precedence (weakest to strongest)

system theme (200)
   < set_css_data / HWG_SETFGCOLOR / HWG_SETBGCOLOR (600)
      < hwg_install_entry_css (800)
         < application theme.css (801)
Golden rule: theme.css always has the final say. If your app loads a theme.css, it overrides the KDE theme, Adwaita and any internal HWGUI CSS.

5.1. How GTK4 chooses the theme

By default, GTK4 queries the xdg-desktop-portal to learn whether the system is in light or dark mode. On KDE, this requires xdg-desktop-portal-kde to be installed: 

sudo apt install xdg-desktop-portal-kde kde-config-gtk-style

After installing, restart the services (note that on Plasma 6 the service name carries the plasma- prefix): 

systemctl --user daemon-reload
systemctl --user restart plasma-xdg-desktop-portal-kde.service
systemctl --user restart xdg-desktop-portal.service

To confirm what the portal is reporting: 

gdbus call --session --dest org.freedesktop.portal.Desktop \
  --object-path /org/freedesktop/portal/desktop \
  --method org.freedesktop.portal.Settings.Read \
  org.freedesktop.appearance color-scheme

The return value is a uint32:

ValueMeaning
0No preference
1Prefer-dark
2Prefer-light
Warning: if the KDE portal is not installed, GTK4 falls back to the generic backend (gtk.portal) and may choose inconsistent colours — a light window with a dark popover, for example.

5.2. Forcing light or dark

# per execution
GTK_THEME=Adwaita:dark  ./myapp
GTK_THEME=Adwaita:light ./myapp

# global (~/.config/gtk-4.0/settings.ini)
[Settings]
gtk-theme-name=Adwaita
gtk-application-prefer-dark-theme=0

5.3. Custom CSS (theme.css)

Applications can load their own CSS via hwg_CssLoadFile(). It is applied to the display with priority GTK_STYLE_PROVIDER_PRIORITY_USER + 1 (801), which overrides the system theme and the internal HWGUI CSS — including popovers and menus. 

hwg_CssLoadFile( "theme.css" )

5.4. When to use each mechanism

Mechanism Priority When to use
System theme 200 Nothing to do — it is the default. Ideal for utilities that should follow the OS.
HWG_SETFGCOLOR / HWG_SETBGCOLOR 600 Spot colour of a specific widget at runtime. Low precedence, easily overridden.
HWG_CSSLOAD (CSS as a string) 600 Dynamic CSS, generated at runtime (e.g. colours from a database).
hwg_install_entry_css 800 Entry geometry reset (Win32-like behaviour). Avoid putting colours here, so as not to "leak" over theme.css.
HWG_CSSLOADFILE (theme.css) 801 Complete visual identity of the application. Wins over everything. Should cover entry, popover, menu and button if full control is desired.

5.5. Best practices

  1. Utility without its own visual identity: do not load theme.css. Let GTK4 follow the portal and the system theme. Result: consistent window and popovers (all light or all dark, depending on the OS).
  2. Application with a visual identity: load theme.css and cover all states of the widgets you want to control — especially entry, popover, menu and button.
  3. Avoid hard-coded colours in hwg_install_entry_css. If that function only resets geometry (padding, border-width, min-width), do not put background-color or color there — otherwise, even with theme.css loaded, entries will remain white if the app CSS does not cover them.
  4. If theme.css does not cover entries, lower the priority of hwg_install_entry_css to GTK_STYLE_PROVIDER_PRIORITY_APPLICATION (600), so it stops fighting with the theme.
  5. Test with GTK_THEME: GTK_THEME=Adwaita:light and GTK_THEME=Adwaita:dark let you see the behaviour in both modes without restarting the session.
Practical example — theme.css covering the main widgets: 
entry, entry.entry > text {
  background-color: #2b2b2b;
  color: #e0e0e0;
  border-color: #444;
}

popover, popover.background, menu {
  background-color: #2b2b2b;
  color: #e0e0e0;
}

button {
  background-color: #3a3a3a;
  color: #e0e0e0;
  border-color: #444;
}
With this CSS in theme.css, the app controls entries, menus and buttons even when the system is in dark mode.

6. Behaviour differences from GTK2

FeatureGTK2GTK4
File dialog GtkFileChooserDialog, synchronous GtkFileDialog, asynchronous (with a local GMainLoop)
Window layout GtkFixed directly GtkOverlay → GtkBox → GtkFixed (to support background image)
Keyboard events key_press_event / key_release_event GtkEventControllerKey in the CAPTURE phase
Partial redraw gtk_widget_queue_draw_area() gtk_widget_queue_draw() (whole widget)
Window icon gtk_window_set_icon() gdk_toplevel_set_icon_list() on the realize signal
Widget allocation GtkAllocation gtk_widget_get_width/height()
Touch / multitouch Full support on Windows Still limited on Windows; better on Linux/Wayland

7. Known limitations

7.1. Touch on Windows

GTK4 on Windows still shows problems with touch screens: drag-and-drop, window movement with a pen, and event coordinates shifted under HiDPI scaling. For applications that depend on reliable touch on Windows, the native Win32 version of HWGUI remains the best choice.

7.2. Wayland

On Wayland, the window icon is taken from the .desktop file matching the app_id. If the application has no installed .desktop file, the compositor uses a generic icon. The code calls g_set_prgname() in HWG_GTK_INIT to help with this.

7.3. Partial redraw

GTK4 removed gtk_widget_queue_draw_area(). Every invalidation now covers the whole widget. In large editors and browses this may add a small extra redraw cost — imperceptible in practice, but worth knowing.

8. Troubleshooting

8.1. Menu/popover with a different colour from the window

Cause: GTK4 received a dark (or light) theme preference from the system, but hwg_install_entry_css in window.c forces light colours on the entry widgets only. Result: dark popovers over a light window (or the reverse). See section 5 — Themes, appearance and CSS for the full detail.

Diagnosis:

  1. Confirm what the portal reports: 
    gdbus call --session --dest org.freedesktop.portal.Desktop \
  --object-path /org/freedesktop/portal/desktop \
  --method org.freedesktop.portal.Settings.Read \
  org.freedesktop.appearance color-scheme
  2. Test with GTK_THEME=Adwaita:light ./bincnt. If the inconsistency disappears, the internal CSS is forcing colours.

Solutions (pick one):

  1. Install the KDE portal: 
    sudo apt install xdg-desktop-portal-kde kde-config-gtk-style
systemctl --user daemon-reload
systemctl --user restart plasma-xdg-desktop-portal-kde.service
systemctl --user restart xdg-desktop-portal.service
  2. Remove hard-coded colours from hwg_install_entry_css in window.c, keeping only geometry (padding, border-width, min-width, border-radius). This way entries follow the same theme as the rest of the window.
  3. Load a theme.css in the app covering entry, popover and menu. Since theme.css goes to priority 801, it overrides the internal HWGUI CSS.

9. Guidelines for contributors

  1. Do not mix GTK2 and GTK4 in the same file. If you need different behaviour, create a separate file with a _gtk4 suffix or place it under source/gtk4/.
  2. Do not use toolkit #ifdef. Source code must be pure for each backend.
  3. Always add a Changelog entry before committing. Use the convention: + for additions, * for modifications, - for removals.
  4. Prefer creating *_gtk4.c/.prg files over duplicating whole libraries. One specific file under source/common/editor/, for instance, is easier to maintain than a full copy of procmisc.hbp.
  5. Test on KDE and GNOME before considering a UI change "ready".
  6. Document API changes in this README and in the Changelog.
  7. When touching CSS, respect the priority hierarchy. Do not put hard-coded colours in providers with priority 800/801 without covering every related widget — otherwise the result is a theme mix.
