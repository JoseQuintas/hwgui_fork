HWGUI GTK4 — Guia de Uso

Portabilidade do HWGUI de GTK2 para GTK4.
Este documento descreve os princípios, as diretivas e o uso dos recursos GTK4 no HWGUI.

1. Visão geral

O HWGUI é uma biblioteca GUI para Harbour que oferece uma API única para aplicações Win32 e Linux (GTK). A versão GTK4 é um port paralelo à GTK2, mantendo a compatibilidade da API no nível Harbour — ou seja, o mesmo código de aplicação compila em ambos os backends.

1.1. Por que GTK4?

  • GTK2 está em fim de vida — sem suporte moderno e sem integração com Wayland, HiDPI e temas contemporâneos.
  • GTK4 oferece melhor integração com KDE, GNOME e Wayland via xdg-desktop-portal.
  • Suporte nativo a HiDPI, escalonamento e aceleração por GPU.
  • Compatível com Harbour Unicode de forma transparente.

1.2. Princípios do port

  1. Paralelismo, não substituição. GTK2 e GTK4 coexistem no mesmo repositório. A aplicação escolhe qual linkar.
  2. Sem poluição com #ifdef. Código específico de cada toolkit vive em arquivos separados, não em ramos condicionais no mesmo arquivo.
  3. API Harbour inalterada. O código do usuário não precisa saber se está sobre GTK2 ou GTK4.
  4. Cada toolkit tem seu diretório e seu .hbp. source/gtk4/ para o backend novo; source/common/ só para o que compila em todos os toolkits.

2. Estrutura de arquivos

CaminhoDescrição
source/gtk4/ Implementação dos widgets, janelas, diálogos e controllers GTK4.
include/hwgtk4.h Cabeçalho com as definições específicas do backend GTK4.
hwguiGTK4.hbp / .hbc / .hbm Arquivos de projeto e build do backend GTK4. Geram lib/hwgui.a.
procmiscGTK4.hbp Lib utilitária (editor, processamento) para GTK4. Gera lib/procmisc.a.
utils/bincnt/bincntGTK4.hbp Gerenciador de containers binários compilado contra GTK4.
source/common/editor/hcedit_l_gtk4.c Editor de texto (Linux) portado para GTK4.
Regra prática: se um arquivo usa APIs exclusivas do GTK4 (GtkFileDialog, gtk_widget_get_width(), g_list_model_*, etc.), ele deve ficar em source/gtk4/ ou ter um sufixo _gtk4.

3. Compilando

3.1. Requisitos

  • GTK 4.10+ (idealmente 4.20+ para GtkFileDialog)
  • Harbour 3.2+ com suporte a hb_thread
  • pkg-config e gtk4.pc instalados
# Verificar GTK4
pkg-config --modversion gtk4

# Verificar Harbour
harbour --version

3.2. Compilar a biblioteca HWGUI

A lib é gerada com o nome lib/hwgui.a, tanto para GTK2 quanto para GTK4 — o que distingue os dois backends é o .hbp usado no build, não o nome do arquivo gerado. 

cd hwgui

# Backend GTK2
hbmk2 hwgui.hbp
# Produz: lib/hwgui.a (compilada com GTK2)

# Backend GTK4
hbmk2 hwguiGTK4.hbp
# Produz: lib/hwgui.a (compilada com GTK4) — sobrescreve a anterior
Atenção: as duas versões produzem lib/hwgui.a no mesmo caminho. Não é possível manter GTK2 e GTK4 instalados ao mesmo tempo no mesmo diretório. Para alternar entre backends, é preciso recompilar a lib a partir do .hbp correspondente.

3.3. Compilar as libs utilitárias

O mesmo vale para as libs utilitárias: o .hbp específico do backend gera lib/procmisc.a em ambos os casos. 

# Backend GTK2
hbmk2 procmisc.hbp
# Produz: lib/procmisc.a (GTK2)

# Backend GTK4
hbmk2 procmiscGTK4.hbp
# Produz: lib/procmisc.a (GTK4) — sobrescreve a anterior

3.4. Compilar uma aplicação do usuário

A aplicação referencia o .hbc correspondente ao backend que deseja usar. Como as libs têm o mesmo nome (hwgui.a, procmisc.a), o .hbc é quem aponta para o caminho correto — e a aplicação linka com o mesmo nome de biblioteca nos dois casos.

Backend .hbc a incluir Libs linkadas
GTK2 hwgui.hbc + procmisc.hbc lib/hwgui.a, lib/procmisc.a
GTK4 hwguiGTK4.hbc + procmiscGTK4.hbc lib/hwgui.a, lib/procmisc.a
Implicação prática: como as libs têm o mesmo nome, o .hbc é quem determina qual backend será usado no link. Certifique-se de recompilar lib/hwgui.a e lib/procmisc.a com o backend desejado antes de compilar a aplicação.

Exemplo de meuappGTK4.hbp:

# meuappGTK4.hbp

{linux}hwguiGTK4.hbc
{linux}procmiscGTK4.hbc

-L.

-n -w1

-omeuapp

meuapp.prg

O .hbc adiciona -lhwgui -lprocmisc ao link, mas aponta para o caminho onde as libs GTK4 estão. Ou seja, o nome do .a é o mesmo, mas o conteúdo é GTK4.

4. Usando GTK4 no código Harbour

A API de alto nível (classes HWindow, HDialog, HButton, HGet, HBrowse etc.) é idêntica entre GTK2 e GTK4. O código abaixo funciona nos dois backends: 

#include "hwgui.ch"

FUNCTION Main()
   LOCAL oWnd, oBtn

   INIT WINDOW oWnd TITLE "Exemplo GTK4" SIZE 400, 200

   @ 20, 20 BUTTON oBtn CAPTION "Clique" SIZE 120, 30 ;
      ON CLICK { || hwg_MsgInfo( "Olá GTK4!" ) }

   ACTIVATE WINDOW oWnd
RETURN Nil
Dica: para testar a mesma aplicação nos dois backends, basta ter dois arquivos .hbp — um linkando hwgui.hbc e outro linkando hwguiGTK4.hbc.

5. Temas, aparência e CSS

O GTK4 tem um sistema de estilos em cascata (CSS) com múltiplas camadas de prioridade. Entender essa hierarquia é essencial para prever qual cor vai vencer quando duas regras se aplicam ao mesmo widget.

5.0. Hierarquia de CSS no GTK4

Cada provider de CSS é registado com uma prioridade. Quanto maior o número, mais tarde ele é aplicado e, portanto, mais ele vence em caso de conflito.

Constante Valor Quem usa no HWGUI GTK4
GTK_STYLE_PROVIDER_PRIORITY_FALLBACK 1 Reservado ao GTK (fallback interno).
GTK_STYLE_PROVIDER_PRIORITY_THEME 200 Tema do sistema (Adwaita claro/escuro, Breeze, etc.).
GTK_STYLE_PROVIDER_PRIORITY_SETTINGS 400 Configurações do utilizador (ex.: gtk-theme-name).
GTK_STYLE_PROVIDER_PRIORITY_APPLICATION 600 set_css_data() em control.c — usado por HWG_SETFGCOLOR, HWG_SETBGCOLOR e HWG_CSSLOAD.
GTK_STYLE_PROVIDER_PRIORITY_USER 800 hwg_install_entry_css() em window.c — reset de geometria dos entries (e, no código atual, também cores claras fixas).
USER + 1 801 HWG_CSSLOADFILE em control.c — o theme.css da aplicação.

Precedência efetiva (do mais fraco ao mais forte)

tema do sistema (200)
   < set_css_data / HWG_SETFGCOLOR / HWG_SETBGCOLOR (600)
      < hwg_install_entry_css (800)
         < theme.css da aplicação (801)
Regra de ouro: o theme.css tem sempre a última palavra. Se o seu app carrega um theme.css, ele vence o tema do KDE, o Adwaita e qualquer CSS interno do HWGUI.

5.1. Como o GTK4 escolhe o tema

Por padrão, o GTK4 consulta o xdg-desktop-portal para saber se o sistema está em modo claro ou escuro. No KDE, isso requer o xdg-desktop-portal-kde instalado: 

sudo apt install xdg-desktop-portal-kde kde-config-gtk-style

Depois de instalar, reinicie os serviços (note que no Plasma 6 o serviço tem o prefixo plasma-): 

systemctl --user daemon-reload
systemctl --user restart plasma-xdg-desktop-portal-kde.service
systemctl --user restart xdg-desktop-portal.service

Para confirmar o que o portal está a reportar: 

gdbus call --session --dest org.freedesktop.portal.Desktop \
  --object-path /org/freedesktop/portal/desktop \
  --method org.freedesktop.portal.Settings.Read \
  org.freedesktop.appearance color-scheme

O retorno é um uint32:

ValorSignificado
0Sem preferência
1Prefer-dark
2Prefer-light
Atenção: se o portal KDE não estiver instalado, o GTK4 cai no backend genérico (gtk.portal) e pode escolher cores inconsistentes — janela clara com popover escuro, por exemplo.

5.2. Forçando claro ou escuro

# por execução
GTK_THEME=Adwaita:dark  ./meuapp
GTK_THEME=Adwaita:light ./meuapp

# global (arquivo ~/.config/gtk-4.0/settings.ini)
[Settings]
gtk-theme-name=Adwaita
gtk-application-prefer-dark-theme=0

5.3. CSS customizado (theme.css)

Aplicações podem carregar um CSS próprio via hwg_CssLoadFile(). Ele é aplicado no display com prioridade GTK_STYLE_PROVIDER_PRIORITY_USER + 1 (801), o que sobrescreve o tema do sistema e o CSS interno do HWGUI — inclusive para popovers e menus. 

hwg_CssLoadFile( "theme.css" )

5.4. Quando usar cada mecanismo

Mecanismo Prioridade Quando usar
Tema do sistema 200 Nada a fazer — é o padrão. Ideal para utilitários que devem seguir o SO.
HWG_SETFGCOLOR / HWG_SETBGCOLOR 600 Cor pontual de um widget específico durante a execução. Baixa precedência, fácil de sobrescrever.
HWG_CSSLOAD (CSS em string) 600 CSS dinâmico, gerado em tempo de execução (ex.: cores do banco de dados).
hwg_install_entry_css 800 Reset de geometria dos entries (comportamento Win32-like). Evite colocar cores aqui, para não "vazar" sobre o theme.css.
HWG_CSSLOADFILE (theme.css) 801 Identidade visual completa da aplicação. Vence tudo. Deve cobrir entry, popover, menu e button se quiser controle total.

5.5. Boas práticas

  1. Utilitário sem identidade visual própria: não carregue theme.css. Deixe o GTK4 seguir o portal e o tema do sistema. Resultado: janela e popovers coerentes (tudo claro ou tudo escuro, conforme o SO).
  2. Aplicação com identidade visual: carregue theme.css e cubra todos os estados dos widgets que quer controlar — especialmente entry, popover, menu e button.
  3. Evite cores fixas em hwg_install_entry_css. Se essa função só serve para resetar a geometria (padding, border-width, min-width), não coloque background-color nem color ali — caso contrário, mesmo com o theme.css carregado, os entries vão continuar brancos se o CSS do app não os cobrir.
  4. Se o theme.css não cobrir entries, baixe a prioridade de hwg_install_entry_css para GTK_STYLE_PROVIDER_PRIORITY_APPLICATION (600), para que ele deixe de brigar com o tema.
  5. Teste com GTK_THEME: GTK_THEME=Adwaita:light e GTK_THEME=Adwaita:dark permitem ver o comportamento nos dois modos sem reiniciar a sessão.
Exemplo prático — theme.css cobrindo os widgets principais: 
entry, entry.entry > text {
  background-color: #2b2b2b;
  color: #e0e0e0;
  border-color: #444;
}

popover, popover.background, menu {
  background-color: #2b2b2b;
  color: #e0e0e0;
}

button {
  background-color: #3a3a3a;
  color: #e0e0e0;
  border-color: #444;
}
Com este CSS em theme.css, o app controla entries, menus e botões mesmo quando o sistema está em dark mode.

6. Diferenças de comportamento em relação ao GTK2

RecursoGTK2GTK4
Diálogo de arquivo GtkFileChooserDialog síncrono GtkFileDialog assíncrono (com GMainLoop local)
Layout de janela GtkFixed direto GtkOverlay → GtkBox → GtkFixed (para suportar background image)
Eventos de teclado key_press_event / key_release_event GtkEventControllerKey na fase CAPTURE
Redraw parcial gtk_widget_queue_draw_area() gtk_widget_queue_draw() (widget inteiro)
Ícone de janela gtk_window_set_icon() gdk_toplevel_set_icon_list() no sinal realize
Alocação de widget GtkAllocation gtk_widget_get_width/height()
Toque / multitouch Suporte completo no Windows Ainda limitado no Windows; melhor em Linux/Wayland

7. Limitações conhecidas

7.1. Toque no Windows

O GTK4 no Windows ainda apresenta problemas com telas de toque: arrastar-e-soltar, movimentação de janelas com caneta e coordenadas de eventos deslocadas em escalas HiDPI. Para aplicações que dependem de toque confiável no Windows, a versão Win32 nativa da HWGUI continua sendo a melhor escolha.

7.2. Wayland

No Wayland, o ícone de janela é obtido do arquivo .desktop correspondente ao app_id. Se a aplicação não tiver um .desktop instalado, o compositor usa um ícone genérico. O código chama g_set_prgname() em HWG_GTK_INIT para ajudar nisso.

7.3. Redraw parcial

O GTK4 removeu gtk_widget_queue_draw_area(). Toda invalidação é feita no widget inteiro. Em editores e browses grandes isso pode gerar um pequeno custo extra de redraw — imperceptível na prática, mas vale saber.

8. Solução de problemas

8.1. Menu/popover com cor diferente da janela

Causa: o GTK4 recebeu do sistema a preferência de tema dark (ou light), mas o hwg_install_entry_css em window.c força cores claras apenas nos entry. Resultado: popovers escuros sobre janela clara (ou o inverso). Ver secção 5 — Temas, aparência e CSS para o detalhe completo.

Diagnóstico:

  1. Confirme o que o portal reporta: 
    gdbus call --session --dest org.freedesktop.portal.Desktop \
  --object-path /org/freedesktop/portal/desktop \
  --method org.freedesktop.portal.Settings.Read \
  org.freedesktop.appearance color-scheme
  2. Teste com GTK_THEME=Adwaita:light ./bincnt. Se a incoerência desaparecer, é o CSS interno forçando cores.

Soluções (escolha uma):

  1. Instalar o portal KDE: 
    sudo apt install xdg-desktop-portal-kde kde-config-gtk-style
systemctl --user daemon-reload
systemctl --user restart plasma-xdg-desktop-portal-kde.service
systemctl --user restart xdg-desktop-portal.service
  2. Remover cores fixas de hwg_install_entry_css em window.c, deixando apenas geometria (padding, border-width, min-width, border-radius). Assim os entries seguem o mesmo tema do resto da janela.
  3. Carregar um theme.css no app que cubra entry, popover e menu. Como o theme.css vai para a prioridade 801, ele vence o CSS interno do HWGUI.

9. Diretivas para contribuidores

  1. Não misture GTK2 e GTK4 no mesmo arquivo. Se precisa de comportamento diferente, crie um arquivo separado com sufixo _gtk4 ou coloque em source/gtk4/.
  2. Não use #ifdef de toolkit. O código-fonte deve ser puro para cada backend.
  3. Sempre adicione entrada no Changelog antes de commitar. Use a convenção: + para adição, * para modificação, - para remoção.
  4. Prefira criar arquivos *_gtk4.c/.prg em vez de duplicar libs inteiras. Um arquivo específico em source/common/editor/, por exemplo, é mais fácil de manter do que uma cópia inteira de procmisc.hbp.
  5. Teste em KDE e GNOME antes de considerar uma mudança de UI "pronta".
  6. Documente mudanças de API neste README e no Changelog.
  7. Ao mexer em CSS, respeite a hierarquia de prioridades. Não coloque cores fixas em providers de prioridade 800/801 sem cobrir todos os widgets relacionados — ou o resultado vai ser uma mistura de temas.
